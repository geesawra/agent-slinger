# Image messages and previews

Consulted Paseo `30178c4f58b67f8472901356e1484022bd835de0` (2026-09-27), especially `packages/protocol/src/messages.ts`, `packages/client/src/daemon-client.ts`, `packages/server/src/server/agent/prompt-attachments.ts`, `packages/server/src/server/session/files/workspace-files-session.ts`, `packages/app/src/assistant-image/file-acquisition.ts`, `docs/architecture.md`, and `docs/protocol-compatibility.md`.

## Wire behavior

- `send_agent_message_request` accepts optional `images: [{data, mimeType}]`; `data` is base64. It also carries `text`, `messageId`, and optional `activeTurnBehavior`. Image-only prompts are valid: the daemon's `buildAgentPrompt` makes image content blocks even when trimmed text is empty.
- `agent.create.request` accepts the same optional `images` array alongside `initialPrompt` and `clientMessageId`. Oesap uses it only after `server_info.features.creationLifecycle` advertises managed creation. An uncertain creation retry uses the same idempotency key, client message ID, text, and image bytes.
- `user_message` timeline items contain text, optional `messageId`, and optional `clientMessageId`; the server's `recordSubmittedPrompt` stores only text. Image bytes sent by the user cannot be recovered from authoritative timeline history. Oesap overlays acknowledged local images on matching user messages during the current app session and never treats that overlay as server history.
- Assistant image output may be a Markdown image source in `assistant_message.text`. Host file sources use `file_explorer_request` (`cwd`, `path`, `mode: "file"`, `maxBytes`) and a correlated `file_explorer_response`. Oesap omits `acceptBinary`, selecting the legacy JSON base64 response, validates `kind: "image"`, encoding, MIME, byte count, and size, and reads host paths only. Relative paths resolve against the agent's `cwd` (or project root when it is absent); absolute paths outside that root use filesystem root as `cwd`, matching Paseo's preview-target behavior. Direct data and HTTP(S) sources are handled by the image renderer.

## Compatibility and bounds

Image fields are optional in Paseo's send and create schemas. There is no advertised image-send capability in the consulted `server_info.features` schema, so Oesap sends this established field on supported requests and surfaces a host refusal. Managed creation remains gated by `creationLifecycle`; a send retry is offered only with `agentRequestReceipts` because that feature supplies deduplication receipts. Unknown timeline fields remain harmless.

Oesap holds at most six outgoing images of 2 MiB each, limits preparation input to 20 MiB and 2048 pixels per edge, requests at most 8 MiB for a host image preview, and allows a 32 MiB incoming WebSocket message for base64 JSON and relay wrapping. Filename is local UI metadata and is never sent in the Paseo image object. Local draft image bytes are discarded on explicit disconnect or a change of host identity; results from an old connection or selected thread are rejected after an async preview read.

On iPhone, the composer accepts images from Photos, Files, and image paste. File and Photos imports read no more than 20 MiB before preparation; pasted bytes are checked before decoding. Preparation corrects orientation, scales to at most 2048 pixels on either edge, strips source metadata, and emits PNG when transparency fits or JPEG otherwise. The attachment strip shows locally prepared thumbnails, allows removal, and opens the same full-screen zoomable viewer as received images. Text-only, image-only, and mixed prompts use the same send path. The send button waits for pending preparation, and a failed or uncertain send keeps its original image bytes for retry while later draft edits remain separate.

## Markdown image rendering

Remote message bodies use MarkdownUI 2.4.1 with its pinned cmark-gfm 0.9.0 parser. Parsing runs on a serial actor; the original Markdown source remains available unchanged while a streamed body is reparsed. Image nodes are rewritten only in a display-only cmark tree to opaque per-message IDs, so the Markdown library's default image loaders never receive host-provided URLs. HTTP(S) reads use an ephemeral cookie-free session, reject credentials and unsafe redirects, and stop after 8 MiB. Data URLs are accepted only as bounded base64 `image/*`; `blob:` and executable/custom schemes are rejected. Host files go through the scoped Paseo file RPC, never the phone filesystem.

Composer Markdown is edited in `NativeImagePasteTextView` and styled live with the pinned cmark-gfm parser. Its accessibility value and text storage retain the Markdown source. The composer does not resolve Markdown image URLs; outgoing images remain explicit attachments in the composer strip.

Markdown image-only paragraphs render as tappable thumbnails. Mixed paragraphs are split around each image into text and image blocks so the image itself opens the full-screen viewer; surrounding emphasis and link segments are retained. Images inside headings and table cells stay inline and have a separate “View image” action because MarkdownUI's inline image provider supplies only an `Image`, which cannot carry an individual tap action in a mixed text run. The viewer supports zoom and pan, exposes alt text, and offers retry for failed loads. HTML remains literal MarkdownUI content and is never executed.

Focused tests exercise image-only send and creation serialization, client message IDs in history and live events, bounded host file reads, draft clearing and immutable retry after edits, host and thread selection changes, and image preparation bounds and transparency. The current Paseo timeline still omits sent image bytes, so thumbnails for previously sent images are limited to the current local session unless the daemon starts persisting those attachments.
