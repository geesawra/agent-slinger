# Paseo mobile feature gap review

Reviewed 2026-09-26 against the official `getpaseo/paseo` repository at commit
[`d7b7016cc98da02ce5110fb218c70cac419657f3`](https://github.com/getpaseo/paseo/commit/d7b7016cc98da02ce5110fb218c70cac419657f3).
This compares Oesap's checked-in iPhone MVP with Paseo's cross-platform mobile/web client and its daemon protocol. The [Paseo product brief](https://github.com/getpaseo/paseo/blob/d7b7016cc98da02ce5110fb218c70cac419657f3/docs/product.md) names the central loop: give an agent a task, understand its work, provide direction, and review the result. Priorities below favor completing that loop on a phone over copying the whole desktop environment.

## What Oesap already covers

The [README](../README.md) and implementation show direct or relay host connection, Keychain-backed connection material, project discovery, project-scoped agent lists, a cross-project agent status snapshot, new agent creation with a first prompt, paged timeline history plus live updates, text sending, simple allow/deny permissions, structured tool-call viewing, context use, and provider quota snapshots. The [MVP protocol note](protocol-mvp.md) records the existing capability gates and subscription behavior. These are real native flows; the feature gap is about control, resilience, and broader work context, not missing basic chat.

Oesap's current `RemoteProject`/`RemoteThread` navigation is project → thread, and new threads use the project root as `cwd` ([workspace UI](../Sources/Oesap/Features/WorkspaceViews.swift), [creation adapter](../Sources/Oesap/Protocol/PaseoProtocolClient.swift)). Paseo now models project → workspace → sessions: a workspace can contain multiple agents, terminals, browsers, and diffs, and can use an existing directory or managed worktree ([workspaces guide](https://github.com/getpaseo/paseo/blob/d7b7016cc98da02ce5110fb218c70cac419657f3/public-docs/workspaces.md), [mobile panels](https://github.com/getpaseo/paseo/blob/d7b7016cc98da02ce5110fb218c70cac419657f3/docs/mobile-panels.md)). That mismatch matters when a project has several worktrees: a flat thread list hides which checkout a session is changing, and a new root-based thread may land outside the intended workspace.

## Recommended slices, in order

| Priority | Slice and user value | Protocol feasibility and acceptance check |
| --- | --- | --- |
| **P0** | **Stop and deliberately steer a running agent.** A person who sees a wrong command needs a visible Stop action; a follow-up sent during an active turn needs a clear choice of whether to interrupt or steer. | The official schema exposes `cancel_agent_request` and `send_agent_message_request.activeTurnBehavior` (`interrupt` or `steer`); the TypeScript client uses both ([wire schema](https://github.com/getpaseo/paseo/blob/d7b7016cc98da02ce5110fb218c70cac419657f3/packages/protocol/src/messages.ts#L1190-L1207), [cancel schema](https://github.com/getpaseo/paseo/blob/d7b7016cc98da02ce5110fb218c70cac419657f3/packages/protocol/src/messages.ts#L1802-L1807), [client](https://github.com/getpaseo/paseo/blob/d7b7016cc98da02ce5110fb218c70cac419657f3/packages/client/src/daemon-client.ts#L3423-L3518)). Oesap's service exposes only `send(agentID:text:)` and omits `activeTurnBehavior`; the current daemon defaults that omission to `interrupt` ([handler](https://github.com/getpaseo/paseo/blob/d7b7016cc98da02ce5110fb218c70cac419657f3/packages/server/src/server/session.ts#L8035-L8088)). Thus text sends can already replace a running turn, but the UI does not explain that consequence or offer `steer`. Accept when Stop is shown for a running turn, its receipt/error and resulting status are visible, active-turn send behavior is explicit, and a failed steer retains the draft. Keep one message ID across an uncertain retry so a repeated send cannot duplicate the prompt; verify behavior against the supported daemon and provider. |
| **P0** | **Finish structured attention requests in Oesap.** Today a question or other structured request tells the user to answer in Paseo, interrupting the phone workflow. Start with question choices/free text and plan actions that have explicit labels. | Permission requests carry `kind`, `input`, `suggestions`, and `actions`; responses can carry `selectedActionId` or `updatedInput` ([schema](https://github.com/getpaseo/paseo/blob/d7b7016cc98da02ce5110fb218c70cac419657f3/packages/protocol/src/messages.ts#L450-L487)). Upstream has a mobile question form that submits `updatedInput.answers` ([form](https://github.com/getpaseo/paseo/blob/d7b7016cc98da02ce5110fb218c70cac419657f3/packages/app/src/components/question-form-card.tsx#L393-L436)). Oesap preserves the raw input only as displayed JSON and maps the first allow/deny actions ([adapter](../Sources/Oesap/Features/PaseoConnectionFactory.swift)). Accept when known question shapes render selectable answers, custom text, and validation; action labels and IDs are preserved; unknown shapes still explain the limitation; failed responses retain the user's choices. Do not invent a universal form for arbitrary provider metadata. |
| **P0** | **Keep unsent work through app relaunch.** A phone session is often interrupted. Oesap preserves a draft during transient connection loss in memory, but `OesapModel` is the only draft owner. | This is local-only and requires no new daemon operation. Persist drafts by verified host ID plus agent ID or a new-thread intent, exclude secrets from logs/backups as appropriate, and clear only on acknowledged send or explicit discard. Accept when a draft survives force quit/relaunch, host switching never shows another host's draft, and an uncertain new-agent creation keeps its idempotency identity and avoids a duplicate initial prompt. Inspect current [draft and creation state](../Sources/Oesap/Features/OesapModel.swift) before choosing storage. |
| **P1** | **Show the real workspace around each session.** Group agents under workspaces with branch/path and active work status; start a new agent in the selected existing workspace. A later flow may create a local or worktree workspace. | Current wire operations include paged `fetch_workspaces_request`, `workspace_update`, `workspace.create.request`, and `agent.create.request.workspaceId` ([schema](https://github.com/getpaseo/paseo/blob/d7b7016cc98da02ce5110fb218c70cac419657f3/packages/protocol/src/messages.ts#L1268-L1297), [workspace create](https://github.com/getpaseo/paseo/blob/d7b7016cc98da02ce5110fb218c70cac419657f3/packages/protocol/src/messages.ts#L2595-L2639), [agent create](https://github.com/getpaseo/paseo/blob/d7b7016cc98da02ce5110fb218c70cac419657f3/packages/protocol/src/messages.ts#L1683-L1712)). Gate multiplicity/creation behavior by advertised features and follow the [compatibility contract](https://github.com/getpaseo/paseo/blob/d7b7016cc98da02ce5110fb218c70cac419657f3/docs/protocol-compatibility.md#L31-L41). Accept when two workspaces in one project stay distinct, selecting an agent restores its workspace context, and new agents use the selected workspace ID. Only add worktree creation after listing/selection works end to end. |
| **P1** | **Review changed files without leaving the phone.** A compact, read-only changes list and bounded diff viewer directly supports checking an agent's result. A file explorer can follow as a separate slice. | Paseo exposes `checkout_status_request`, `checkout.diff.get.request`, and `file_explorer_request` ([diff schema](https://github.com/getpaseo/paseo/blob/d7b7016cc98da02ce5110fb218c70cac419657f3/packages/protocol/src/messages.ts#L2141-L2168), [file schema](https://github.com/getpaseo/paseo/blob/d7b7016cc98da02ce5110fb218c70cac419657f3/packages/protocol/src/messages.ts#L2699-L2728)); its compact layout includes a file-explorer destination ([mobile panels](https://github.com/getpaseo/paseo/blob/d7b7016cc98da02ce5110fb218c70cac419657f3/docs/mobile-panels.md)). Accept when a selected workspace shows git/non-git states honestly, diffs are bounded and selectable, binary/oversize files have explicit states, and browsing a file never executes or opens remote content automatically. Keep editing and commit/discard actions for a later reviewed scope. |
| **P1** | **Attach a photo or screenshot to a prompt.** This is useful for a mobile-first client reporting UI bugs or sharing visual context. | `send_agent_message_request` and agent creation both accept base64 `images` with MIME type ([message schema](https://github.com/getpaseo/paseo/blob/d7b7016cc98da02ce5110fb218c70cac419657f3/packages/protocol/src/messages.ts#L1190-L1207), [create schema](https://github.com/getpaseo/paseo/blob/d7b7016cc98da02ce5110fb218c70cac419657f3/packages/protocol/src/messages.ts#L1683-L1702)). Accept when Photos/Files selection offers a preview and removal, conversion honors size limits, send failure retains the attachment, and the app asks for photo access only when needed. Check provider support before promising that every agent can interpret images. |
| **P2** | **Manage long-lived sessions.** Rename/archive/search can keep a large host usable; a terminal is useful for advanced workflows but adds binary framing, keyboard controls, resize ownership, and security-sensitive command execution. | `update_agent_request` and `archive_agent_request` exist ([schema](https://github.com/getpaseo/paseo/blob/d7b7016cc98da02ce5110fb218c70cac419657f3/packages/protocol/src/messages.ts#L917-L937)); terminal operations and binary streaming are described in the [architecture](https://github.com/getpaseo/paseo/blob/d7b7016cc98da02ce5110fb218c70cac419657f3/docs/architecture.md#L300-L309). Accept rename/archive only after definitive RPC outcomes, with confirmation for archive and archived visibility. Treat terminal as a distinct project once workspace identity and review surfaces are stable. |


## Secondary mobile capabilities

- **Foreground recovery (next resilience slice):** Paseo verifies all registered host connections when the app becomes visible, without closing healthy sockets ([runtime](https://github.com/getpaseo/paseo/blob/d7b7016cc98da02ce5110fb218c70cac419657f3/packages/app/src/runtime/host-runtime.ts#L2476-L2485), [bootstrap](https://github.com/getpaseo/paseo/blob/d7b7016cc98da02ce5110fb218c70cac419657f3/packages/app/src/navigation/host-runtime-bootstrap.ts#L255-L263)). Oesap refreshes the Agents overview on foreground, but host reconnect elsewhere is user-driven. Add app-wide, cancellation-aware verification and visible timeline recovery after the core controls; test background/foreground with a dropped socket and an intact socket.
- **Markdown reading and copy (small UI slice):** Paseo renders assistant Markdown, highlighted code, turn copying, and a code-block copy button ([message](https://github.com/getpaseo/paseo/blob/d7b7016cc98da02ce5110fb218c70cac419657f3/packages/app/src/components/message.tsx#L1500-L1540), [code block](https://github.com/getpaseo/paseo/blob/d7b7016cc98da02ce5110fb218c70cac419657f3/packages/app/src/components/highlighted-code-block.tsx#L60-L108)). Oesap currently uses selectable plain text. Add safe, native Markdown presentation and Copy for message/code content after validating long code, links, and VoiceOver; keep remote markup inert.
- **QR relay pairing (convenience):** Paseo's native mobile app scans a pairing offer with the camera ([scanner](https://github.com/getpaseo/paseo/blob/d7b7016cc98da02ce5110fb218c70cac419657f3/packages/app/src/app/pair-scan.tsx#L111-L184)); the hosted browser flow cannot be inferred from that native route. Oesap already accepts a pasted pairing link, so camera scanning can follow the core workflow.
- **Several hosts (later architecture slice):** Paseo has a host registry and host-scoped workspace routes ([registry](https://github.com/getpaseo/paseo/blob/d7b7016cc98da02ce5110fb218c70cac419657f3/packages/app/src/runtime/host-runtime.ts#L1454-L1495), [architecture](https://github.com/getpaseo/paseo/blob/d7b7016cc98da02ce5110fb218c70cac419657f3/docs/architecture.md#L106-L116)). Oesap stores one connection. Add host switching only with per-host credentials, drafts, subscriptions, and state isolation; the current one-host MVP remains usable.
- **Dictation and voice mode (defer):** Paseo documents speech-to-text and conversational voice, and its composer has dictation controls ([voice guide](https://github.com/getpaseo/paseo/blob/d7b7016cc98da02ce5110fb218c70cac419657f3/public-docs/voice.md), [controls](https://github.com/getpaseo/paseo/blob/d7b7016cc98da02ce5110fb218c70cac419657f3/packages/app/src/components/dictation-controls.tsx)). iOS keyboard dictation already supplies text input to Oesap's composer; a separate voice session adds audio transport and host speech configuration, so it is not required for the first native release.

## Boundaries and evidence

This is a source and documentation comparison at the pinned commit. An attempted visit to `https://app.paseo.sh/` rendered only the JavaScript shell and the browser webview could not attach, so interactive hosted PWA inspection was not completed. It verifies that the current Paseo mobile/web client and wire schema contain these flows; it does **not** prove every feature works against every Paseo daemon or provider. A private authenticated host, representative workspaces, and physical iPhone were not available for end-to-end checks. Before implementing each slice, capture the connected daemon's `server_info.features`, test the relevant request/response and subscription lifecycle with sanitized fixtures, then validate the native flow on a simulator and a real host. Capability decisions belong at Oesap's protocol boundary; [Paseo's compatibility rules](https://github.com/getpaseo/paseo/blob/d7b7016cc98da02ce5110fb218c70cac419657f3/docs/protocol-compatibility.md#L31-L41) call for an explicit unavailable state when a feature is unsupported.
