# Agent stop and active-turn send protocol

Checked on 2026-09-27 against the official Paseo commit
[`d7b7016cc98da02ce5110fb218c70cac419657f3`](https://github.com/getpaseo/paseo/commit/d7b7016cc98da02ce5110fb218c70cac419657f3), which was still upstream `HEAD` that day. The checked-in `@getpaseo/server` and `@getpaseo/protocol` packages report version **0.9.2**. This note defines the verified contract for Oesap's Stop, Interrupt, and Steer slice. It does not establish a minimum compatible daemon version for steering: Paseo advertises no dedicated steering feature flag.

## Wire contract

All operations use Oesap's existing `{"type":"session","message":{...}}` envelope and correlated request IDs.

| Action | Request message | Response payload | Meaning |
| --- | --- | --- | --- |
| Stop current run | `cancel_agent_request {agentId, requestId}` | `cancel_agent_response {requestId, agentId, agent: AgentSnapshot or null, error?: string or null}` | Supply `requestId`, although the schema permits omission for legacy clients. A non-null error means Stop failed. A null error can also mean the run had already ended: the response has no `cancelled` flag. Use the returned snapshot when present and reconcile with the live stream or a fresh snapshot. |
| Send while active | `send_agent_message_request {requestId, agentId, text, messageId?, activeTurnBehavior?: "interrupt" or "steer"}` | `send_agent_message_response {requestId, agentId, accepted: boolean, error: string or null}` | `accepted: true` acknowledges dispatch, not turn completion. An omitted behavior defaults to `interrupt` in the current daemon. Supply a client `messageId` for receipt-based deduplication. |

The shapes are defined in [Paseo's schema](https://github.com/getpaseo/paseo/blob/d7b7016cc98da02ce5110fb218c70cac419657f3/packages/protocol/src/messages.ts#L1349-L1359), [Stop request](https://github.com/getpaseo/paseo/blob/d7b7016cc98da02ce5110fb218c70cac419657f3/packages/protocol/src/messages.ts#L1802-L1806), and [responses](https://github.com/getpaseo/paseo/blob/d7b7016cc98da02ce5110fb218c70cac419657f3/packages/protocol/src/messages.ts#L4790-L4797). The upstream [client](https://github.com/getpaseo/paseo/blob/d7b7016cc98da02ce5110fb218c70cac419657f3/packages/client/src/daemon-client.ts#L3423-L3457) creates a fresh request ID, sends a message ID, checks `accepted`, and correlates the reply by request ID; its [Stop call](https://github.com/getpaseo/paseo/blob/d7b7016cc98da02ce5110fb218c70cac419657f3/packages/client/src/daemon-client.ts#L3496-L3520) checks the response error. The daemon's [send handler](https://github.com/getpaseo/paseo/blob/d7b7016cc98da02ce5110fb218c70cac419657f3/packages/server/src/server/session.ts#L8034-L8119) and [Stop handler](https://github.com/getpaseo/paseo/blob/d7b7016cc98da02ce5110fb218c70cac419657f3/packages/server/src/server/session.ts#L4602-L4644) confirm those outcomes. Both operations require `workspace.write` or `hub.execute` under the current [authorization map](https://github.com/getpaseo/paseo/blob/d7b7016cc98da02ce5110fb218c70cac419657f3/packages/server/src/server/authorization/operation-permissions.ts#L28-L35).

## Behavior and compatibility

`interrupt` replaces an active run. `steer` asks the provider to admit a follow-up into the same foreground turn. If there is no active turn, the daemon starts a normal turn. If the provider says steering is unavailable, the daemon falls back to interrupt-and-replace. If the provider throws, the result can be ambiguous and the daemon does **not** fall back or retry. [Paseo's provider contract](https://github.com/getpaseo/paseo/blob/d7b7016cc98da02ce5110fb218c70cac419657f3/docs/providers.md#L110-L116) and [manager implementation](https://github.com/getpaseo/paseo/blob/d7b7016cc98da02ce5110fb218c70cac419657f3/packages/server/src/server/agent/agent-manager.ts#L2724-L2767) make this distinction. Codex, Claude, OpenCode, and Pi have provider-specific steering paths; plugin providers and other sessions may not. A successful send receipt does not tell the client whether the provider steered or the daemon replaced the run.

There is **no** `server_info.features.steer` flag in the inspected protocol. Do not invent one or treat `agentRequestReceipts` as a steering flag. An older daemon can ignore the additive `activeTurnBehavior: "steer"` field and run the legacy interrupt path; [upstream's compatibility test](https://github.com/getpaseo/paseo/blob/d7b7016cc98da02ce5110fb218c70cac419657f3/packages/protocol/src/messages.active-turn-behavior.test.ts#L60-L86) demonstrates that behavior. The app therefore must not promise that a Steer choice will always preserve the active turn. If the product requires that guarantee, it needs an upstream advertised capability or a documented daemon floor first. Stop and the existing send RPC have no new feature gate in the current schema. The current Stop handler returns a successful no-op when the agent has no in-flight run and an error when cancellation is refused ([lifecycle command](https://github.com/getpaseo/paseo/blob/d7b7016cc98da02ce5110fb218c70cac419657f3/packages/server/src/server/agent/lifecycle-command.ts#L58-L109)).

## Message identity and recovery

The daemon advertises `server_info.features.agentRequestReceipts` in version 0.9.2; the schema says the flag was added in v0.8.0 ([feature schema](https://github.com/getpaseo/paseo/blob/d7b7016cc98da02ce5110fb218c70cac419657f3/packages/protocol/src/messages.ts#L3527-L3533), [advertisement](https://github.com/getpaseo/paseo/blob/d7b7016cc98da02ce5110fb218c70cac419657f3/packages/server/src/server/websocket-server.ts#L1788-L1792)). When `messageId` is supplied, the daemon keys a durable receipt by `(agentId, messageId)` and fingerprints the normalized prompt plus the effective behavior. Repeating a **completed** identical intent returns without sending again. Reusing the ID with changed text, attachments, or behavior produces `agent_request_key_conflict`; a still-pending receipt produces `agent_request_outcome_unknown` rather than blindly replaying ([receipt service](https://github.com/getpaseo/paseo/blob/d7b7016cc98da02ce5110fb218c70cac419657f3/packages/server/src/server/message-receipts/index.ts#L20-L55), [tests](https://github.com/getpaseo/paseo/blob/d7b7016cc98da02ce5110fb218c70cac419657f3/packages/server/src/server/message-receipts/index.test.ts#L19-L54)).

Use a new `requestId` for each wire attempt, but keep an uncertain send's `agentId`, `messageId`, text, attachments, and behavior immutable. Editing the draft or choosing a different behavior creates a **new** intent with a new message ID. On a host without `agentRequestReceipts`, the same message ID is accepted by the schema but durable deduplication is unverified; do not automatically resend after a timeout. Even on a capable host, a pending receipt can mean the provider received the message without an acknowledgement. Preserve the draft, inspect authoritative timeline/history after reconnect, and explain the ambiguity before any deliberate retry. The successful send response only confirms admission, so timeline recovery remains authoritative for visible content.

Stop has no turn ID or idempotency key. Disable duplicate Stop taps while a request is pending. If its response is lost, fetch/reconcile the agent state; do not automatically repeat Stop, because a new turn could have started in the meantime and the second request could cancel it. A successful Stop response can be a no-op when the run had already ended. Do not claim that the run stopped solely because `error` is null.

## Oesap implementation

The [protocol client](../Sources/Oesap/Protocol/PaseoProtocolClient.swift) generates a fresh request ID per call and preserves the caller's `messageID` and chosen `activeTurnBehavior` in each explicit send. It checks response agent identity, acceptance, and nonempty errors. Stop checks both the response agent ID and returned snapshot ID, accepts a null snapshot without claiming completion, and maps a valid snapshot into the [native service adapter](../Sources/Oesap/Features/PaseoConnectionFactory.swift). The legacy `send(agentID:text:)` still emits the omitted behavior shape for compatibility. The new service overloads have unsupported defaults, so a replacement service cannot silently discard intent identity or mode.

The [model](../Sources/Oesap/Features/OesapModel.swift) stores an in-memory immutable send intent per host and thread. An unconfirmed send retains its draft; a changed draft does not change the pending intent. Manual retry requires receipt support on both the original and currently connected host and reuses the same message ID, text, and behavior. Connection changes invalidate outstanding action tokens, and late completions are checked against the connection generation. Stop has a pending state that suppresses duplicate taps, checks the latest thread-state revision, and waits for authoritative status when the response is null or a newer state update has arrived. This state is in memory only; app relaunch loses the pending intent, which is why draft persistence remains a separate roadmap item.

The [chat UI](../Sources/Oesap/Features/ChatView.swift) uses a native, scrollable sheet for the three-way active-send and uncertain-delivery choices, with a visible Cancel action. A three-button native alert clipped Cancel at AX5 accessibility text size in simulator inspection. Stop and permission confirmations remain native two-action alerts. This is a presentation choice; it does not alter the wire or retry semantics.

## Validation boundary

The offline simulator unit suite passed **91 tests** in `.build/agent-control-ax-sheet-r4.xcresult` on 2026-09-27. Focused fixtures cover explicit request encoding, correlated response and agent IDs, refusal and null Stop snapshots, immutable same-ID retry with an edited draft, receipt-capability downgrade, host and thread isolation, connection-loss and late-completion races, duplicate Stop suppression, unverified host identity, and changed live state during Stop. These fixtures use synthetic prompts and IDs. Across the focused AX5 run, broader regression run, functional reruns, and native audit, **20 distinct UI tests passed**: `.build/agent-control-ax-sheet-r4.xcresult`, `.build/agent-control-ui-regression.xcresult`, `.build/agent-control-ui-final.xcresult`, and `.build/agent-control-audit-prominent.xcresult`. The first broad run had five failing tests that were corrected and rerun; there was no audit suppression. The final Release simulator build passed (`.build/agent-control-release-final-r3.log`). The protocol contract was checked against official daemon 0.9.2 source; the tests do not run that daemon or prove provider steering. No authenticated live daemon, relay, or physical iPhone was available. Validate Stop, provider-specific steering/fallback, ambiguous receipts, and reconnection against a disposable live host before claiming end-to-end control behavior.
